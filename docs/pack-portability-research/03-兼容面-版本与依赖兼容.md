# 03 · 兼容面：一个包「还能不能用」怎么判断、不匹配会怎样

- 全局运行时全在启动器 userData 下：main.ts:367-376（dsh-runtime、node-runtime、pnpm-runtime、plugin-sources），插件池 main.ts:588/750/760/786（userData/plugin-store）。**复制 dsh-packs 不会带走这些。**
- 包内实测结构：.credentials.yaml（+2 bak）、AGENTS.md、attachments/、cache/、channel-pack/、config/、data/、extras/、llm-deepseek/、logs/、openai-gateway/、our-free-model/、plans/、**profiles/**、relays/、remote-web-ui-registry/、rewind-snapshots/、sessions/、skills/、skills-manager/、state/、storages/、ui-blocks/；**没有 settings.yaml**（只有 settings.yaml.imported）
- profiles/ 下实测 4 项：node_modules（**整份 DSH 内核，npm 布局**）、node_modules.bak-stage2-20261023（迁移残留）、dsh-origin-3080（活动 profile）、web（过期 profile，profile.yaml 还写 0.2.0-rc.2）
- 所以「随包内核」在代码里指 **profiles/node_modules**（instances.ts:140），不是 userData/dsh-runtime/versions

## 1. dshVersion 从哪来、怎么校验；回落顺序

### 来源（四处，互相不校验）

1. packs.json：pack-registry.ts:24-25（dshVersion?: string，注释「要求的 DSH 精确版本」）
2. profile.yaml：pack-verify.ts:531、pack-snapshot.ts:765-766、pack.ts:229-231
   实测 dsh-origin-3080：dshVersion: 0.2.1-rc.2，且 name 是「major place」（含空格、与目录名不同）
3. 包清单：pack-manifest.ts:42-46、303-307（缺 dshVersion 直接抛）
4. 官方包推断：official-pack.ts:50/140/199

### 校验强度：只校验格式，不校验存在性

- settings.ts:133-136 validRuntimeVersion 只匹配 ^v?\d+\.\d+\.\d+(-pre)?$
- settings.ts:280/310 用它过滤，非法置 null
- pack-manifest.ts:303-307 同类格式校验
- **没有任何一处把「声明版本」与「实际会跑的内核」比对**

### 回落顺序（instances.ts:134-148 packKernel）

1. 包内 profiles/node_modules（kernelIn，instances.ts:120-126）：找 .bin/dsh.cmd|dsh.exe|dsh，版本读 @deepseek-ai/dsh/package.json
2. 否则用声明版本找 <dshInstallPath>/versions/<record.dshVersion>/node_modules（instances.ts:143-146；路径口径 runtime-versions.ts:185-187）
3. 都没有才回落 settings.launchExecutable（instances.ts:147）

随后 settingsFor 写进每包 settings：launchExecutable / launchArgs=['web'] / dshVersion（instances.ts:388-396）。

启动器侧另有全局内核发现顺序（dsh-install.ts:163-180 findInstalledDsh）：
老布局 node_modules/.bin/dsh.cmd → 新布局 versions/<ver> 取最高 → 系统 PATH（含 APPDATA\npm、PNPM_HOME、ProgramFiles\nodejs）。

守卫：runtime.ts:389-411 —— 配置仍是 npx 形态（settings.ts:338-341 usesOnDemandDsh）时，拉起前再探一次；探不到就报「没有可用内核」并拒绝启动。
托管安装：runtime-versions.ts:194-203 ensureDshVersionInstalled（缺就联网装）、installer.ts:698-747。

## 2. 插件依赖装在哪？换机器后还有效吗？

- 每个 profile 自己的 node_modules + 指向包内 plugin-bodies 的 junction；pnpm store 是**启动器全局的**（userData/plugin-store）
- 依赖声明：实测 profiles/dsh-origin-3080/package.json 形如 "<pkg>": "file:./.dsh-launcher-plugin-bodies/<pkg>"，共 19 条
- 安装命令：installer.ts:563-608 调 dsh plugin --profile <id> add ...，环境 DSH_HOME=当前包（:604）、store-dir 指插件池（:605-606）
- profile 级 .npmrc 会被写入**绝对路径** store-dir：installer.ts:233-252（:248）
- 实测这个包没有 .npmrc / .pnpm / .modules.yaml —— 是「实体目录 + junction 门层」形态：
  - profiles/<id>/node_modules 顶层 19 条 junction，**全部绝对目标**，都指向包内
  - 整包 150 条 reparse point：130 条 → profiles\node_modules\...，20 条 → profiles\<id>\...（全在包内；台式 482 条 %APPDATA%\npm **未核实**）
  - profiles/node_modules（内核）顶层 junction = 0，纯文件树
- 导出时包外链接被**静默丢弃**：pack-snapshot.ts:338-346 resolveLink（目标不在 home 内 return null）
- 导入端**重建 node_modules 门层**：pack-snapshot.ts:983-1029 rebuildBodyGates
  关键注释（:967-976）：DSH 的 resolveBundleDir 只认 installAnchor 的 node_modules 与 profiles/<id>/package.json，**完全不读 dependencies 里的 file: 值**，缺门层 = cannot resolve profile bundle = 插件全灭
- 结论：**导出 zip → 导入**这条路依赖有效（本体随包、门层重建）；**直接复制包目录无效**（junction 存绝对路径，路径一变门层全断）

## 3. 不匹配时的实际行为

### (a) 版本不匹配：静默

- packKernel 拿到 versions/<声明版本> 目录时不比对里面 package.json 的版本（instances.ts:143-146 只判断 .bin 是否存在）
- 声明版本目录不存在时直接回落全局内核（instances.ts:147），无日志/告警；settingsFor 用 kernel.version ?? base.dshVersion 覆盖声明值（:395），声明值就此消失
- 唯一读真实版本的是凭据格式判定：dsh-credentials-compat.ts:128-167（从可执行文件向上 7 层找 @deepseek-ai/dsh/package.json）
- 自检第 5 条**比错了对象**：pack-verify.ts:614-623 拿 profile.yaml 的 dshVersion 去比启动器随包内核目录（默认 resources/kernels，:97-101、:246 listKernels），既不比 versions/<ver>，也不比真正会跑的 profiles/node_modules
  实测反例：本机 runtime/kernels 只有 0.2.0-rc.2，而这个包 profile.yaml 与包内内核都是 0.2.1-rc.2（正在跑）→ 自检第 5 条会判 **fail「缺内核」，纯误报**

### (b) 插件 enabled 但依赖缺失：分层，最后一段静默

- 判定：profile-service.ts:262-273 missingDependencies 只看 profiles/<id>/node_modules/<pkg>/package.json 在不在
- 切 profile 补装：profile-service.ts:553-580 → main.ts:585-712（先复用同 home 其他 profile / 共享 bodies，再按 receipt 重装，再试共享 store 离线装；**都没有就静默 continue**，main.ts:694）
- 运行期：DSH 起得来，插件加载失败（SKIPPED_BUNDLE / CANNOT_FIND_MODULE / PATCH_ENTRY_NOT_FOUND）
- 启动器**不在启动前自检**：verifyPackHome 只在导入后跑一次（ipc.ts:1037-1047，失败也绝不判导入失败）和用户手点自检（ipc.ts:1073-1081）
- 长期隐患：AI 尝试安装（ai-install.ts:272/1493/1957-1959）由 agent 直接 plugin add，**不写插件 receipt**（recordPluginInstall 只在 installer.ts:858/1063/1131）→ 换机后这类插件无法按来源重建

### (c) 导入期会改全局设置（同机假设的典型）

- ipc.ts:1030-1033 先 ensureDshVersionInstalled（缺就**联网下载**内核）再导入
- pack.ts:1444-1454 调 selectDshVersion，:1470-1475 把**全局 settings 的 dshVersion 改成被导入包的版本**

## 4. 包内 node 运行时是否平台/架构绑定、有没有记录

- **包里没有 node**：实测 profiles/node_modules/.bin/dsh.cmd 是 IF EXIST "%dp0%\node.exe" ... ELSE SET "_prog=node"
- 启动器替它补：node-runtime.ts:740-745 requiresNodeRuntime 把 dsh.cmd 也算「需要 node」→ runtime.ts:416-420 prepareNodeRuntime 并注入 PATH
- 托管 node **只在 Windows 上存在且写死 win**：node-runtime.ts:249-256 永远返回 node-<ver>-win-<arch>.zip；:266-269 识别也要求 -win-(x64|arm64)；:109-127 取 node.exe
  → **win-x64 的托管 node 换到 arm64 或非 Windows 必然不可用**（同一目录名会被认成「已安装」，直到 execFile 探测失败才暴露）
- 打包态的随包 node 其实不可用（代码注释自述）：main.ts:72-79 —— electron-builder 会剥掉 node_modules，发布版走「本机 Node ≥22.13 → 托管下载」
- 内核本身（profiles/node_modules）**没有任何平台/架构标记**，只有版本号；里面含原生模块（@img、@swc、@koromix 等）→ 跨 OS/架构直接搬 = 原生模块废掉
- 唯一写下的平台记录形同虚设：pack-snapshot.ts:54-58 SnapshotMeta.platform，导出时写 process.platform（:541）；**全仓无任何读取点**；插件 receipt 的平台字段一律 'unknown'（pack.ts:676/1373/1583/1763）

## 5. 结论：一个包要真正适配另一台机器

### 必须随包携带

1. 整份 DSH 内核 profiles/node_modules（npm 实体树，实测 0 junction，可搬）—— packKernel 第一优先级
2. 插件本体 profiles/<id>/.dsh-launcher-plugin-bodies/<pkg> + package.json 里相对化的 file: 依赖
3. profile 元数据 profiles/<id>/profile.yaml、package.json
4. 链接清单 dsh-snapshot.json（links 必须全在包内，pack-verify.ts:348-364）

### 必须重新生成

1. **所有 junction**（本机 150 条，绝对目标）；重建代码只在导入路径（pack-snapshot.ts:930-957、983-1029），**搬目录这条路没有对应步骤**
2. profile 级 .npmrc 的 store-dir（installer.ts:248 写绝对路径；导出会剥掉，手工复制则残留 → ERR_PNPM_UNEXPECTED_STORE，installer.ts:619-651 有自动迁移兜底）
3. node 运行时（目标机无 ≥22.13 系统 Node 且非托管命中 → 只能联网下载）
4. 全局内核版本目录 versions/<ver>（若包只声明版本而不带 profiles/node_modules）

### 必须在导入时校验（现状几乎只有自检，且自检不拦、不自洽）

1. 声明 dshVersion ↔ 真正会用的内核（现在不比，且自检第 5 条比错对象）
2. 平台/架构（SnapshotMeta.platform 已写未读）
3. 链接全部可解析到包内（pack-verify 第 3 条做了，但只报告不阻断）
4. 每个 enabled 插件的门层 + 入口 + 依赖（第 1/4/6 条做了，同样只报告）
5. 包外依赖泄漏（第 2 条做了）
6. 注册表与清单在**包外**：packs.json 在 %APPDATA%\dsh-launcher，pack-manifests 在 userData → 包目录不自描述，homePath 写绝对路径；跨机只能走导出 zip → 导入，不能指望「拷目录 + 拷注册表」自动对上

一句话：**包能带的都带了（内核 + 插件本体 + 链接清单），真正断的是两样东西 —— 绝对路径的 junction，和没人校验的「声明版本 vs 实际内核 / 平台架构」。**
